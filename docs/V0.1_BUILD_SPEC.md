# Aviation Passport — V0.1 Build Specification

## Product mission

V0.1 proves one complete loop:

**Worker creates Aviation Passport → Employer creates Open Demand → System finds compatible workers → Employer views permitted Passport → Employer sends structured opportunity → Worker responds.**

A second worker-facing loop is included from the start:

**Passport + active market demand → My Value estimate.**

The goal is not feature completeness. The goal is to make the core interaction feel materially better than CV/job-board recruitment.

---

## Product constitution

1. Workers use the core platform free.
2. Employers pay for market intelligence and talent access.
3. A worker owns one portable professional identity.
4. Information should be entered once and increasingly self-maintain through employer attestations.
5. Structured aviation data replaces CV interpretation wherever possible.
6. Compensation is transparent.
7. Workers control visibility and contact.
8. Qualifications and ratings are trust marks only when evidence has been checked.
9. Employers can always view aggregate market intelligence; individual talent access requires active Open Demand.
10. Matching is two-way and explainable.
11. Recruitment friction is removed, not digitised.
12. Objective automation happens before the human conversation; human judgement stays human.

---

# Core visual language

**Blue dot** = aircraft experience exists.

**Gold star** = verified aircraft type rating / licence endorsement exists.

**Custom green shield** = current verified company authorisation exists.

There is no separate "verified tick" on these icons. The badge itself is the trust mark.

---

# Supply object: Aviation Passport

## 1. Professional identity

- First name
- Last name
- Professional headline
- Current city/country
- Nationality / nationalities
- Nationality visibility control
- Preferred display currency
- Profile visibility
- Market status
- Optional profile image
- Optional short professional summary

### Visibility modes

- Public
- Aviation network
- Anonymous market
- Private

### Market status

- Not open
- Open to selected opportunities
- Actively looking
- Contract only

Nationality is separate from work rights. Nationality can be shown, employer-only, or hidden at product/UI level.

---

## 2. Work rights

Per country:

- Work-right status
- Visa type if relevant
- Expiry if relevant
- Sponsorship required?
- Evidence
- Verification status

Commercial matching should normally use work rights, not nationality.

Citizenship becomes a hard criterion only where legally/contractually relevant, such as defence/security-clearance eligibility.

---

## 3. Licences & ratings

Licence fields:

- Issuing authority
- Country
- Licence scheme
- Category / privileges
- Licence number (private by default)
- Issue date
- Expiry where applicable
- Limitations
- Evidence
- Verification status

Rating fields:

- Official authority wording
- Mapped aircraft family
- Optional variant
- Optional engine
- Privilege/category
- Evidence
- Verification status

**Gold star is derived only from a verified mapped rating.**

Do not force FAA, CASA, EASA, UK CAA, GCAA etc. into a fake universal licence system. Preserve original credential wording and separately map it to platform-normalised aircraft data.

---

## 4. Aircraft experience

Aircraft experience is linked to employment.

Per exposure record:

- Employer/employment
- Aircraft family
- Optional variant
- Optional engine
- Discipline
- Environment via employment
- Exposure level
- Exposure start/end
- Last worked on
- Employer-confirmed status

Exposure levels:

- Primary
- Regular
- Occasional
- Limited

Do not treat four calendar years of occasional exposure as equal to four years of primary exposure.

**Blue dot is derived from supported aircraft exposure.**

---

## 5. Environment

Shared controlled taxonomy used by worker records and employer demand:

- Line Maintenance
- Base Maintenance
- Heavy Maintenance
- Production
- Final Assembly Line
- Prototype / Development
- Flight Test
- Modification / Retrofit
- Component / Workshop
- Engine Shop
- Structures
- MRO Support
- Field Support
- Other

The label is intentionally "Environment", not "Maintenance Environment".

---

## 6. Employment history

- Employer
- Optional linked verified organisation
- Job title
- Discipline
- City/country
- Employment type
- Start/end date
- Current role
- Environments
- Aircraft exposure
- Optional short description
- Employer confirmation

Long-term flow:

**Structured role accepted → employment record created automatically → employer confirms additional aircraft exposure/training/authorisations over time → Passport self-maintains.**

Employers issue attestations; they do not own or directly rewrite the worker's career history.

---

## 7. Training, competencies and authorisations

Keep these separate:

**Training = what the worker completed.**

**Competency = what the worker can do.**

**Authorisation = what an organisation currently permits the worker to do.**

Examples:

- Human Factors
- EWIS
- Fuel Tank Safety
- Dangerous Goods
- Engine Ground Run
- Towing / Brake Riding
- Borescope
- NDT
- Fibre-optic repair
- Wiring repair
- Company certifying authorisations

Authorisations can be aircraft-specific.

**Green shield is derived from a current verified company authorisation mapped to the aircraft.**

Historical authorisations remain historical facts after expiry/revocation; the current shield disappears.

---

## 8. Market preferences

- Earliest start
- Notice period
- Relocation willingness
- International willingness
- FIFO willingness
- Desired employment types
- Location preferences
- Roster preferences
- Private minimum compensation
- Compensation visibility

Compensation visibility:

- Private
- Compatibility only
- Visible

Default should be **compatibility only**.

Employer sees "compensation compatible" without learning the worker's private floor.

# Demand object: Open Demand

One Open Demand record represents a real requirement for a defined number of people.

Example:

**20 × CASA B2 A320 engineers — Brisbane**

Fields:

- Organisation
- Internal title
- Public title
- Profession
- Discipline
- Seniority
- Positions required
- Positions remaining
- Status
- Visibility
- Employment type
- Location
- Sponsorship availability
- Relocation assistance
- Expected start
- Target fill date
- Roster
- Description

Statuses:

- Draft
- Open
- Paused
- Needs confirmation
- Filled
- Cancelled

Only **Open** demand counts as live market demand.

Positions remaining is the live unit of demand.

---

## Demand requirements

Each requirement uses one of four levels:

- Mandatory
- Trainable
- Preferred
- Not relevant

### Aircraft requirement

Per aircraft:

- Experience requirement
- Rating requirement
- Authorisation requirement
- Minimum exposure
- Maximum months since exposure
- Optional variant/engine

### Licence requirement

- Authority
- Scheme
- Category
- Requirement level
- Whether conversion is accepted

### Competency/training requirement

- Competency/training
- Requirement level
- Must be current?
- Notes

### Environment requirement

- Environment
- Requirement level

This shared data vocabulary lets the system compare supply and demand without parsing prose.

# Employer access rule

## Intelligence mode

Paid employers may view anonymised/aggregated market data even without active hiring:

- Supply counts
- Receptive supply
- Active demand
- Supply/demand ratio
- Licence distribution
- Aircraft experience
- Location
- Availability
- Compensation benchmarks
- Trends

They cannot browse identifiable individual workers.

## Recruitment mode

Individual worker access is unlocked only when the employer has **active Open Demand**.

The demand must be tied to candidate search and every employer approach.

**No Open Demand = no individual talent access.**

This prevents talent fishing and ensures the system captures real labour demand.

Employers must not receive direct broad database SELECT access to Passport tables. Talent access goes through a controlled matching service/RPC.

---

# Open Demand visibility

### Public
Opportunity can be publicly discoverable.

### Limited
Contributes to aggregate market demand; sensitive employer/details are restricted.

### Confidential
Exists and counts as real demand but is not publicly listed. Appropriate details are revealed only to approached candidates.

Analytics must use aggregation thresholds so confidential fleet/base strategy cannot be reverse-engineered.

# Compensation model

Every monetary component stores:

- Amount minimum
- Amount maximum
- Native currency
- Period
- Component type
- Optional taxable flag
- Notes

Examples:

- AED 32,000/month base salary
- AED 7,500/month housing
- AUD 18,000/year super
- USD 8,000 one-off relocation

The native currency remains authoritative.

Each user has a preferred display currency. UI conversion happens automatically while retaining the original value.

## Future Compensation Intelligence

Three worker-facing layers:

1. Original package
2. Converted package
3. Purchasing-power-adjusted value

Later include tax, housing, schooling, medical, pension/super, travel, leave and household assumptions.

Purchasing-power-adjusted values must be labelled estimates, never fake precision.

# Matching engine V0.1

Do not use black-box AI scoring.

## Layer 1 — hard compatibility

Examples:

- Mandatory licence
- Mandatory aircraft experience
- Required work rights / sponsorship compatibility
- Required environment
- Location/relocation compatibility
- Employment type
- Availability

## Layer 2 — trainable gaps

Examples:

- Type rating the employer provides
- Engine run
- Recurrent EWIS
- Company-specific authorisation

Trainable gaps do not disqualify the candidate.

## Layer 3 — employer preferences

Examples:

- Preferred type rating
- Additional fleet
- Recency
- Seniority
- Extra competencies

## Layer 4 — worker compatibility

- Compensation meets private floor
- Location acceptable
- Employment type acceptable
- Roster acceptable
- Relocation/FIFO acceptable
- Availability compatible
- Worker currently receptive

Matching is always two-way.

---

## Match labels

### Strong Match
All mandatory employer requirements and worker hard preferences align; strong preferred alignment.

### Exact Match
All mandatory employer requirements and worker hard preferences align.

### Trainable Match
Fundamental fit exists; remaining gaps are explicitly trainable.

### Mobility Match
Potential fit after recognised licence conversion, sponsorship or relocation pathway.

### Incompatible
A genuine non-negotiable condition fails.

The UI explains the result instead of showing a mysterious AI percentage.

An internal score may be used only for sorting.

# Employer live-market feedback

While creating Open Demand, employer sees supply change as requirements change.

Example:

CASA B2 → 612

+ A350 experience mandatory → 183

+ recent within 24 months → 109

+ A350 rating mandatory → 31

System can show:

**Making A350 rating mandatory reduces compatible supply by 72%.**

Switching rating to Trainable/Preferred immediately expands the pool.

Compensation should eventually behave the same way:

AUD 140–150k → 21 compatible workers

AUD 150–160k → 48

AUD 160–175k → 69

# Opportunity transaction

An employer cannot send generic recruiter spam.

An opportunity is always linked to Open Demand.

Worker receives structured information:

- Employer
- Role
- Location
- Aircraft/environment
- Salary/package
- Roster
- Benefits
- Start timing
- Sponsorship/relocation
- Match explanation
- Trainable gaps

Actions:

- Interested
- Ask question
- Decline

Future stages:

- Interview
- Offer
- Accepted

When accepted, the structured role can pre-populate the new employment record.

---

# My Value

**My Value is V0.1 core**, not a later optional feature.

V0.1 should estimate value from compensation on compatible active Open Demand.

Worker sees:

- Estimated market range
- Confidence / sample size
- Number of compatible open positions
- Demand level
- Factors driving value
- Potential value improvements where supportable

Do not display fake precision.

Example:

**AUD 158k–176k/year**
Based on 14 compatible open-demand compensation records
**Confidence: Limited**

Later My Value incorporates:

- Real offers
- Accepted offers
- Similar verified Passports
- Aircraft/ratings
- Environment
- Recency
- Location
- Work rights
- mobility
- purchasing power

Future scenarios:

- Current local value
- International opportunity value
- Value after type rating
- Value if FIFO accepted
- Value if relocation enabled

# Security architecture

Supabase recommends enabling RLS on exposed tables. V0.1 follows a deny-by-default approach for Passport records.

Worker tables:
- worker can read/write their own data
- no broad employer read policy

Employer tables:
- organisation members manage their organisation/demand

Talent search:
- controlled server endpoint or SECURITY DEFINER RPC
- verifies organisation membership
- verifies active Open Demand
- limits results to candidates relevant to that demand
- respects worker privacy and market status
- returns only permitted fields

Credential files:
- private Storage bucket
- short-lived signed access only where justified
- never public URLs
